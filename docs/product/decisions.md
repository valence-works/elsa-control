# Elsa Commercial Platform Decision Log

This log records product/program decisions that constrain delivery but do not require a full ADR. Status values are `Decided`, `Provisional`, and `Needs owner`.

| Date | Status | Decision | Rationale and consequences | Revisit condition |
|------|--------|----------|----------------------------|------------------|
| 2026-08-29 | Decided | Elsa Cloud is the fully managed Valence-hosted manifestation of Elsa Control. | Prevents a second control plane and maximizes reusable product capability. | Revisit only with evidence that a required SaaS capability cannot fit a mode/provider boundary. |
| 2026-08-29 | Decided | Elsa Control Cloud and self-hosted Elsa Control share the same core domain and provider contracts. | Customer-owned infrastructure remains first-class while SaaS billing/operations stay optional. | Revisit if a concrete security boundary requires a separately deployed service, not a separate domain. |
| 2026-08-29 | Decided | Version, topology, feature set, release channel and isolation are separate selections. | Compatibility and lifecycle evolve independently; frontend policy remains data-driven. | Do not revisit without a domain-model contradiction proven by implementation. |
| 2026-08-29 | Decided | The existing Elsa Control React console is the basis for hosted and self-hosted product modes. | It already contains authentication, workspaces, deployments, packages, artifacts and operations shell. | Revisit only after a documented spike demonstrates an insurmountable hosting/product constraint. |
| 2026-08-29 | Decided | Initial infrastructure work proves one Azure vertical slice before broad SaaS implementation. | The present Azure deployment hosts Elsa Control but does not provision Elsa workloads. | Revisit after the deployment proof is accepted. |
| 2026-08-29 | Decided | Arbitrary packages are prohibited on Shared compute. | NuGet packages are executable code and no shared sandbox guarantee exists. | Revisit only after a security-reviewed sandbox proof and explicit isolation ADR. |
| 2026-08-29 | Decided | `valence-works/elsa-production-image` is the current commercial Elsa 3 image source; `elsa-pro-docker` is historical. | The current pipeline owns Server/Studio/Combined builds with scanning, SBOM, provenance and signing; Elsa Control metadata is stale. | Revisit when an Elsa 4 commercial distribution or replacement image repository is approved. |
| 2026-08-29 | Decided | The deleted `elsa-platform-saas` repository was scaffolding only and is not a migration source. | Its separate provisioning/control-plane premise conflicts with ADR-0006, and no retained implementation is required for the unified product. | Revisit only if an independently preserved artifact is later shown to contain unique, relevant evidence. |
| 2026-08-29 | Decided | Azure Container Apps is the initial Elsa workload compute platform; AKS is deferred. | The #108 West Europe proof validated signed-image pull, managed identity/Key Vault, Azure SQL durability, health-gated multiple revisions, safe reapply and complete cleanup with lower operational burden than Kubernetes. | Revisit only when a concrete networking, isolation, scale, reliability or economics requirement cannot be met safely by Container Apps. |
| 2026-08-29 | Decided | The first deployment proof and initial Elsa Cloud release offer Elsa 3.8 only; the catalog supports an arbitrary number of present and future Elsa versions. | The existing commercial image path makes 3.8 the shortest credible launch. A data-driven, cardinality-unbounded catalog prevents this launch choice from becoming a fixed Elsa 3/4 switch or enum. | Add a version only when its distribution, compatibility and support evidence passes the release gate. |
| 2026-08-29 | Decided | Combined is the default topology for the Elsa 3.8 deployment proof and initial managed offering; Server plus Studio remains a first-class catalog topology. | Combined shortens the first vertical slice without encoding a permanent one-container assumption. | Change the default only with deployment or customer evidence; do not remove the separate topology. |
| 2026-08-29 | Decided | Version lifecycle is `Preview` → `Supported` → `Maintenance` → `End of Support`; Maintenance blocks new instances, End of Support provides a warned migration window, and major upgrades are never forced or silent. | Bounds support obligations without constraining catalog cardinality or unexpectedly breaking customer workloads. | Revisit only if operational evidence requires a more protective policy. |
| 2026-08-29 | Decided | Every Elsa release line receives at least 12 months of Maintenance followed by at least a 6-month End-of-Support migration-grace period; individual release lines may receive longer windows. | Provides a predictable 18-month minimum runway after active support while bounding image retention and support obligations. | Never shorten a published window; extensions are release-specific catalog data. |
| 2026-08-29 | Decided | Instances pin a minor Elsa release line; validated patch releases within that line roll out automatically, while movement to another minor line requires explicit customer approval. Major-version changes remain explicit migrations. | Keeps routine security and reliability fixes current without silently introducing broader compatibility changes. | Patch rollout still requires notice, maintenance-window, emergency and rollback policy. |
| 2026-08-29 | Decided | Standard non-emergency patch releases provide seven days' notice, run in the customer's configured maintenance window and may be deferred once for up to fourteen days. | Gives production customers predictable change control while bounding fleet drift and vulnerability exposure. | Revisit if operating evidence shows the notice or maximum deferral is unsafe or commercially unsuitable. |
| 2026-08-29 | Decided | Critical security or reliability patches receive 24 hours' notice with no deferral; actively exploited vulnerabilities or imminent fleet-safety threats may be patched immediately with notification as soon as practical. Failed health validation triggers automatic rollback. | Protects customers quickly while reserving immediate unannounced change for evidence-backed emergencies. | Emergency classification and every override must be auditable. |
| 2026-08-29 | Decided | Customer-approved minor-line upgrades use a managed staged cutover: preflight, backup, target revision, health validation, quiescence, migration and traffic cutover. Rollback is guaranteed only when the catalog marks the exact transition rollback-compatible; irreversible transitions require an explicit customer gate. | Delivers a managed-service experience without making a false universal rollback promise across schema or state changes. | Revisit if a release-line compatibility contract enables a stronger guarantee. |
| 2026-08-29 | Decided | Major versions use a managed side-by-side migration of portable configuration, secret references, workflow definitions and catalog-certified artifacts. Persisted or running workflow instances are excluded by default and must be drained, completed or cancelled; state migrates only through an explicitly certified transition adapter. | Provides a useful managed migration without promising semantic compatibility that Elsa major versions may not provide. | Expand the portable set or state support only per evidence-backed transition contract. |
| 2026-08-29 | Decided | After a successful major-version cutover, retain the source instance stopped and read-only for 30 days for audit/export, with no traffic or execution; permit early deletion. Executable rollback must occur before final cutover. | Preserves a bounded recovery reference without split-brain execution or indefinite infrastructure cost. | Revisit the duration only with operating-cost and customer-recovery evidence. |
| 2026-08-29 | Decided | The first paid Elsa Cloud release offers Dedicated isolation only: dedicated runtime and database per instance. Shared and Data-isolated are deferred pending executable boundary/noisy-neighbor evidence; arbitrary packages remain gated by Private/custom-code validation. | This is the shortest credible paid launch without making an unproven cross-customer isolation claim. | Add a profile only after #110-derived guarantees and tests pass and its unit economics are understood. |
| 2026-08-29 | Decided | West Europe is the sole initial managed region; primary customer data and backups remain in the EU/EEA. Customer-selected regions and multi-region DR are not launch promises. | Minimizes first-stamp complexity while providing a clear residency boundary. | Add a region after demand, capacity, backup/restore and operational readiness are evidenced. |
| 2026-08-29 | Decided | Stripe Billing/Checkout owns payment transactions; Elsa Control projects entitlements. Launch uses a 14-day trial, no execution-credit metering, seven-day failed-payment grace, then blocks new provisioning/upgrades while workloads remain running/readable; final suspension retains data for 30 days with notice/export before deletion. | Delivers a simple, humane commercial lifecycle without coupling product behavior to pricing-plan names or immediately destroying workloads. | Revisit time windows with fraud, cost and customer-support evidence. |
| 2026-08-29 | Decided | Seamless identity handoff into managed Elsa is required for the walking skeleton, using a short-lived signed one-time exchange rather than a second customer identity system. | A second login contradicts the one-product promise and would harden a temporary trust boundary into UX. | Replace the mechanism only with an equally seamless and more secure standard integration. |
| 2026-08-29 | Decided | Initial production Dedicated instances target 99.9% monthly managed-runtime availability; Preview has no SLO. Standard support is business-hours, with P1 acknowledgement within one hour. Skywalker Digital B.V. (KvK 88244520), operating the Valence Works offering, is the intended contracting entity. | Sets a measurable initial service promise and ties commercial terms to the evidenced Dutch legal entity without claiming 24/7 standard support. | Contractual SLA/credits and support coverage require operating evidence and final legal terms before public launch. |
| 2026-08-29 | Decided | Establish `elsa-workflows/elsaworkflows.io` as the canonical marketing-source repository and deploy it through a GitHub-controlled Cloudflare Pages pipeline; Cloudflare remains DNS/edge. Import the currently deployed source before marketing changes. | The current production bundle is observable but no authoritative GitHub source/pipeline is discoverable; creating one explicit authority restores GitHub as source of truth. | Revisit hosting only if the site requires capabilities Cloudflare Pages cannot provide. |
| 2026-08-29 | Decided | `valence-works/elsa-production-image` owns commercial Elsa image build/release truth; Elsa Control owns the catalog projection. Release metadata must identify exact Elsa/component versions, topology, immutable digest, channel, compatibility, SBOM, provenance and signature. | Prevents mutable `latest` strings and a second hand-maintained catalog from becoming desired-state authority. | Supersede only through an explicit replacement distribution repository/contract. |
| 2026-08-29 | Decided | `elsa-production-image` publishes a signed machine-readable release manifest as the producer-owned ingestion contract; Elsa Control admits only releases whose manifest, immutable image digest, signatures and retained supply-chain evidence verify. | [`elsa-production-image#27`](https://github.com/valence-works/elsa-production-image/issues/27) delivered the contract; #158 and #202 enforce schema 2.0 admission and distinct OCI subject/payload identity, while #208 durably projects safe lifecycle, topology, compatibility and evidence facts for deterministic queries. This preserves Control's projection ownership without reconstructing release truth from tags and source files. | Approve a replacement only through an explicit distribution contract; each new release still requires producer evidence and applicable runtime-integration compatibility. |
| 2026-08-29 | Decided | For the initial Elsa 3.8 proof, Nuplane remains runtime/image-side; Elsa Control owns package intent, metadata and compatibility resolution. Direct Control-to-Nuplane orchestration is deferred to the Private/custom-package workstream. | Avoids blocking deployment proof on an unneeded integration while preserving deterministic runtime package reconciliation. | Revisit through a bounded API/ownership spike before arbitrary-package delivery. |
| 2026-08-29 | Decided | Initial production recovery covers Elsa relational state, immutable desired-state/configuration and artifact references, plus provider metadata; secrets are rebound from provider references. Pre-upgrade backup is mandatory, restore-to-new-instance is first, with 24-hour RPO and 4-hour RTO targets and no launch multi-region DR promise. | Defines a testable recovery boundary without pretending external secrets or global failover are already solved. | Strengthen RPO/RTO or DR only after restore exercises and cost evidence. |
| 2026-08-29 | Decided | Checked-in Bicep/provider modules are production infrastructure source of truth; Aspire remains local orchestration/developer experience. | Keeps production changes reviewable and reproducible without discarding Aspire's development value. | Revisit only if the provider spike proves another declarative source materially safer. |
| 2026-08-29 | Decided | Frontend CI requires install, unit tests, TypeScript typecheck and production build; critical customer flows add browser E2E coverage. No arbitrary percentage coverage threshold is imposed. | Current missing Artifact Console imports prove executable gates matter more than a nominal coverage number. | Add quantitative thresholds only when coverage data identifies a useful regression boundary. |
