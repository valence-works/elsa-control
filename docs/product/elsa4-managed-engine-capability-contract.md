## Capability map

### Health and readiness

- **Elsa 3.8 producer and Control:** The producer maps `/health` and `/alive` in [`MapDefaultEndpoints`](https://github.com/valence-works/elsa-production-image/blob/b8353d1a0048df231d081c58008b754509af94d3/src/ElsaProServer.ServiceDefaults/Extensions.cs#L78), called by the [Combined host](https://github.com/valence-works/elsa-production-image/blob/b8353d1a0048df231d081c58008b754509af94d3/src/ElsaProCombined/Program.cs#L113). The [Combined manifest entry](https://github.com/valence-works/elsa-production-image/blob/b8353d1a0048df231d081c58008b754509af94d3/scripts/build-release-manifest.py#L68) declares `health-endpoints`, `/health` readiness and `/alive` liveness. Control’s Azure provider probes `GET /health`; only the byte-exact value `Healthy` allows candidate promotion. `Degraded` and `Unhealthy` fail readiness; other values, including padded values or line endings, are invalid ([promotion gate](https://github.com/valence-works/elsa-control/blob/25536c65cd3400bee32d5829be054c72904a4f7e/src/Deployment/ElsaControl.Deployment.Azure/AzureBicepProviderRunner.cs#L1752), [byte-exact classification](https://github.com/valence-works/elsa-control/blob/25536c65cd3400bee32d5829be054c72904a4f7e/src/Deployment/ElsaControl.Deployment.Azure/AzureBicepProviderRunner.cs#L2243)).
- **Foundation:** The host maps [`/health/live`](https://github.com/elsa-workflows/elsa-foundation/blob/4c002dadbc3e707546fac9fb7f5521dda7557314/Essentials/apps/Elsa.Foundation.Host/Health/HealthEndpoints.cs#L31) and [`/health/ready`](https://github.com/elsa-workflows/elsa-foundation/blob/4c002dadbc3e707546fac9fb7f5521dda7557314/Essentials/apps/Elsa.Foundation.Host/Health/HealthEndpoints.cs#L36). Readiness returns JSON and checks that all configured shells are active (200 when ready, 503 otherwise). Workbench has a [default-shell readiness endpoint](https://github.com/elsa-workflows/elsa-foundation/blob/4c002dadbc3e707546fac9fb7f5521dda7557314/Essentials/apps/Elsa.Workbench/Readiness/ShellReadinessEndpointExtensions.cs#L15).
- **Status:** The Foundation routes and response semantics have not been mapped to Control’s existing `/health` probe. The mapping is unverified.

### One-time handoff and Studio open

- **Contract and 3.8 producer:** Control’s [#127 contract](https://github.com/valence-works/elsa-control/blob/25536c65cd3400bee32d5829be054c72904a4f7e/docs/spikes/127-managed-elsa-identity-handoff.md#L9) defines the target boundary; implementation evidence here comes from the pinned producer. Its [manifest generator](https://github.com/valence-works/elsa-production-image/blob/b8353d1a0048df231d081c58008b754509af94d3/scripts/build-release-manifest.py#L68) assigns `managed-elsa-handoff-v2` and `managed-elsa-studio-grants-v1` ([capability literals](https://github.com/valence-works/elsa-production-image/blob/b8353d1a0048df231d081c58008b754509af94d3/scripts/release_manifest.py#L27)). The runtime [binds `ManagedElsa:Handoff` options](https://github.com/valence-works/elsa-production-image/blob/b8353d1a0048df231d081c58008b754509af94d3/src/ElsaProServer.Hosting/ManagedElsaRuntimeHandoff.cs#L45), maps start/callback/logout routes ([feature](https://github.com/valence-works/elsa-production-image/blob/b8353d1a0048df231d081c58008b754509af94d3/src/ElsaProServer.Hosting/ManagedElsaRuntimeHandoff.cs#L236)), and uses protected browser state with an S256 PKCE challenge ([start flow](https://github.com/valence-works/elsa-production-image/blob/b8353d1a0048df231d081c58008b754509af94d3/src/ElsaProServer.Hosting/ManagedElsaRuntimeHandoff.cs#L670), [challenge](https://github.com/valence-works/elsa-production-image/blob/b8353d1a0048df231d081c58008b754509af94d3/src/ElsaProServer.Hosting/ManagedElsaRuntimeHandoff.cs#L801)). Redemption creates a runtime session and a separate Studio authentication cookie ([callback](https://github.com/valence-works/elsa-production-image/blob/b8353d1a0048df231d081c58008b754509af94d3/src/ElsaProServer.Hosting/ManagedElsaRuntimeHandoff.cs#L539), [Studio cookie](https://github.com/valence-works/elsa-production-image/blob/b8353d1a0048df231d081c58008b754509af94d3/src/ElsaProServer.Hosting/ManagedElsaRuntimeHandoff.cs#L606)); Combined enables that Studio auth in [Blazor Server mode](https://github.com/valence-works/elsa-production-image/blob/b8353d1a0048df231d081c58008b754509af94d3/src/ElsaProCombined/Program.cs#L111).
- **Lifetime boundaries:** Producer browser-state lifetime defaults to five minutes and is configurable from one to fifteen minutes ([default](https://github.com/valence-works/elsa-production-image/blob/b8353d1a0048df231d081c58008b754509af94d3/src/ElsaProServer.Hosting/ManagedElsaRuntimeHandoff.cs#L102), [bounds](https://github.com/valence-works/elsa-production-image/blob/b8353d1a0048df231d081c58008b754509af94d3/src/ElsaProServer.Hosting/ManagedElsaRuntimeHandoff.cs#L179)). This is distinct from Control’s one-time token lifetime: at the pinned Control revision it defaults to 60 seconds, permits at most five minutes, and separately caps the runtime session at eight hours ([defaults](https://github.com/valence-works/elsa-control/blob/25536c65cd3400bee32d5829be054c72904a4f7e/src/Hosting/ElsaControl.Api/Authentication/ManagedElsaHandoff.cs#L27), [options and validation](https://github.com/valence-works/elsa-control/blob/25536c65cd3400bee32d5829be054c72904a4f7e/src/Hosting/ElsaControl.Api/Authentication/ManagedElsaHandoff.cs#L59)).
- **Foundation Studio:** This is a separate React host. At the pinned Studio revision, its [`StudioAuthBoundary`](https://github.com/elsa-workflows/elsa-foundation-studio/blob/3eef8fa788bfe2ebd4686df0e9a116532c9b0dc9/src/apps/Elsa.Studio.Web/Client/src/app/auth/studioAuth.tsx#L39) uses a provider-agnostic backend auth manager. That is an auth seam, not proof of Control handoff or runtime-session-cookie integration. The Foundation/Studio managed-open flow and ownership are unassessed here; no absence claim is made. They remain subject to [#870](https://github.com/valence-works/elsa-control/issues/870).

### External-engine connector v1

- **Elsa 3.8 and Control:** The historical Combined manifest does not declare connector-v1. Control’s [v1 protocol](https://github.com/valence-works/elsa-control/blob/25536c65cd3400bee32d5829be054c72904a4f7e/docs/protocol/external-engine-connector/v1/README.md#L1) and protocol code define an interoperability contract, but [#499](https://github.com/valence-works/elsa-control/issues/499) still records that no supported runtime connector exists. [#736](https://github.com/valence-works/elsa-control/issues/736) remains explicitly “Backlog, not armed” for an in-image connector.
- **Status:** Connector v1 is a future integration requirement, not an Elsa 3.8 Combined capability. No Elsa 4 connector integration is mapped here; protocol documentation in Control does not establish an engine-side implementation.

### Configuration and secret references

- **Elsa 3.8 producer and Control:** The producer runtime binds `ManagedElsa:Handoff` from configuration ([options](https://github.com/valence-works/elsa-production-image/blob/b8353d1a0048df231d081c58008b754509af94d3/src/ElsaProServer.Hosting/ManagedElsaRuntimeHandoff.cs#L45), [binding](https://github.com/valence-works/elsa-production-image/blob/b8353d1a0048df231d081c58008b754509af94d3/src/ElsaProServer.Hosting/ManagedElsaRuntimeHandoff.cs#L242)). Control’s Container Apps template attaches an instance identity, binds Key Vault references to that identity, and supplies values through environment `secretRef` entries ([identity](https://github.com/valence-works/elsa-control/blob/25536c65cd3400bee32d5829be054c72904a4f7e/infra/azure-production/modules/container-app.bicep#L351), [Key Vault bindings](https://github.com/valence-works/elsa-control/blob/25536c65cd3400bee32d5829be054c72904a4f7e/infra/azure-production/modules/container-app.bicep#L385), [environment binding](https://github.com/valence-works/elsa-control/blob/25536c65cd3400bee32d5829be054c72904a4f7e/infra/azure-production/modules/container-app.bicep#L254)).
- **Security boundary:** Base ADR-0009 requires least-privilege controls at the workload boundary ([accepted decision](https://github.com/valence-works/elsa-control/blob/25536c65cd3400bee32d5829be054c72904a4f7e/docs/adr/0009-extension-code-isolation-policy.md#L29)). The more specific identity-token-endpoint block is scoped by amendments: Amendment 1 is accepted pending merge and applies to Shared ([status and scope](https://github.com/valence-works/elsa-control/blob/25536c65cd3400bee32d5829be054c72904a4f7e/docs/adr/0009-extension-code-isolation-policy.md#L66), [block requirement](https://github.com/valence-works/elsa-control/blob/25536c65cd3400bee32d5829be054c72904a4f7e/docs/adr/0009-extension-code-isolation-policy.md#L100)); Amendment 2 is proposed, applies only to the Valence Dedicated customer-package profile, and is not in force ([status and scope](https://github.com/valence-works/elsa-control/blob/25536c65cd3400bee32d5829be054c72904a4f7e/docs/adr/0009-extension-code-isolation-policy.md#L158), [profile-specific block](https://github.com/valence-works/elsa-control/blob/25536c65cd3400bee32d5829be054c72904a4f7e/docs/adr/0009-extension-code-isolation-policy.md#L191)). Until Amendment 2 merges, #221’s arbitrary-package Dedicated admission remains fail-closed. The template shows identity attachment and platform Key Vault references, but does **not** prove network enforcement.
- **Foundation:** It has a generic [`SecretReference`](https://github.com/elsa-workflows/elsa-foundation/blob/4c002dadbc3e707546fac9fb7f5521dda7557314/Essentials/src/Secrets/Core/Models/SecretModels.cs#L67) and [`ISecretValueResolver`](https://github.com/elsa-workflows/elsa-foundation/blob/4c002dadbc3e707546fac9fb7f5521dda7557314/Essentials/src/Secrets/Core/Contracts/ISecretValueResolver.cs#L10). This does not establish Elsa 4 host environment/config binding, Control orchestration, or network enforcement. Platform-resolved Key Vault values do not require a Foundation Key Vault client; the generic API is neither proof nor evidence of a defect. Those target mappings and enforcement evidence remain unverified.

- The 3.8 Container Apps template shows identity attachment and platform Key Vault references; it does not prove network enforcement. This source map adds no blanket identity-endpoint-block launch gate to the current #508 baseline or an as-yet-undefined managed Elsa 4 profile. Preserve and independently evidence the amendment-specific requirements if their profiles are activated: Shared’s accepted-pending-merge Amendment 1 and the proposed, not-in-force Valence Dedicated customer-package Amendment 2. Until Amendment 2 merges, #221 continues to fail closed for arbitrary Dedicated packages; this document does not claim customer-package admission. #870 still owns the Elsa 4 profile, distribution, Studio/runtime topology and manifest-authority decisions.
- #870 must settle the Elsa 4 distribution, Studio/runtime topology and manifest authority before this contract can name an Elsa 4 producer representation. No field names or deployment topology are proposed here.
- The unverified mappings need owner review; #871 requires linked follow-up issues in the owning repositories for confirmed missing touchpoints, plus Elsa 4 Lead review. No gap issues were filed in this change. Nothing here certifies managed Elsa 4 readiness.
